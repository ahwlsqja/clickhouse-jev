# 0.1.0 — unreleased candidate

**Status: experimental first-release candidate.** This document prepares the release scope; it does not announce a published package, Git tag or GitHub release. The source currently declares version `0.1.0` in [package metadata](../../pyproject.toml) and [the Python package](../../clickhouse_jev/__init__.py).

## Included

- ClickHouse `executable_pool` integration using a Python standard-library worker and row-count-prefixed JSONEachRow blocks.
- Six SQL functions: `jev_eval`, `jev_prob`, `jev`, `jev_choice`, `jev_score` and `jev_score_norm`. They support probability judgments, explicit thresholds, fixed-label choices and ordered scores. See [the SQL wrappers](../../sql/functions.sql) and [function reference](../../README.md#functions).
- Compatible-input grouping, configurable batching, bounded concurrency per worker and output ordering that follows the input rows.
- Strict response validation for model identity, row keys, answer shapes, finite values, probability distributions and choice/score consistency. An invalid or failed batch fails its whole input block before that block is written.
- Configurable size bounds and block deadlines; HTTPS transport and explicit opt-in HTTP; credentials supplied by environment-variable name or file descriptor rather than stored in generated files.
- A source installer, [installation guide](../installation.md), synthetic integration fixtures and a disposable [real-server demo](../../demo/README.md) that requires no external API key.

The project is [MIT licensed](../../LICENSE); applicable attribution is retained in [NOTICE](../../NOTICE).

## Validation scope and limitations

The tested baseline is ClickHouse **26.8.21.10** and Python **3.10.12** in the development Docker image. Python **3.10+** is the declared requirement. The [support matrix](../support.md) distinguishes that requirement from tested environments and explains the custom executable-worker configuration needed on the host.

Public validation uses deterministic mocks, including a real ClickHouse server. It verifies execution behavior and the response contract, not live-model quality. Other ClickHouse versions, managed hosting including ClickHouse Cloud, distributed deployments and particular live provider/model versions remain unverified.

There is no cache, automatic retry or global cost limit. Earlier blocks and already-submitted external requests are not rolled back after a later failure. SQL `LIMIT` is not a billing limit; concurrency is per worker. Model accuracy, probability calibration, repeatability and production performance are not established by the public tests.

## Candidate validation checklist

Run these checks on the exact source commit intended for release and retain their output:

- [ ] Check that package metadata, `clickhouse_jev.__version__`, these notes and the intended release version agree; review the README, installation guide, support matrix, license and notice.
- [ ] Build the development image: `docker build -t clickhouse-jev .`.
- [ ] Run the full offline suite, including ClickHouse integration: `docker run --rm --network none --entrypoint python3 clickhouse-jev -m unittest discover -s tests -v`. Require exit status 0 and confirm the ClickHouse integration cases actually ran rather than being skipped.
- [ ] Run the server demo: `docker compose up --build --exit-code-from demo --attach demo`. Require exit status 0 and the `Demo passed` result assertions.
- [ ] Run the deliberate API-error demo: `JEV_DEMO_MOCK_MODE=error docker compose up --no-build --force-recreate --exit-code-from demo --attach demo`. Confirm the demo container exits with status 1 and reports `Demo failed: ClickHouse query failed`; a startup failure alone is not this check. The [CI workflow](../../.github/workflows/ci.yml) contains the exact assertions.
- [ ] Remove disposable demo resources with `docker compose down --volumes`, including after a failed run.
- [ ] Confirm the installed worker paths, SQL functions, credential delivery and small-query behavior in the intended deployment. If a live endpoint is part of the release claim, verify its exact response model and all three judgment kinds explicitly; mock success alone is insufficient.

Passing this checklist produces validation evidence for a candidate. Publication is a separate action; these notes remain unreleased until that action occurs.
